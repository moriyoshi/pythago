Native Unicode and buffer reads without metadata caches, 2026-11-17

Compiler-derived layouts: CPython 3.13.18 (GIL) and 3.14.10 (free-threaded),
Linux arm64/amd64. Definitions contain immutable ABI offsets and bit masks;
per-object state is only the owned Unicode reference or active Py_buffer export.
Unicode length, kind flags, and data pointers are loaded on each access.
Buffer accessors load the corresponding native export fields each time.

Pinned access microbenchmarks: Linux arm64, Cortex-X925 cores 5-8,
GOMAXPROCS=4, Go 1.26.11, CGO_ENABLED=0, three 400 ms samples, medians.
Text is Aé🤖日本語 (six code points). Buffer is four bytes from a Python exporter.
APIAndDo controls use the current shared FFI and reproduce per-access Python
entry, a Go mutex, and the Unicode C API. They are simultaneous controls,
not comparisons against a historical binary. These timings measure access,
not complete channel message throughput.

Native read speedup against APIAndDo control:
  Len: FT 23.9x; GIL 25.9x
  Rune: FT 24.7x; GIL 26.5x
  Runes: FT 17.5x; GIL 18.6x

Remaining costs: String/Buffer mutex and bounds/lifetime checks; Runes allocates
one independent Go rune slice. Constructing, cloning, slicing, converting to
UTF-8, and releasing Python objects still require Python entry. Buffer export
and release retain their C API calls. The shared FFI currently allocates an
argument slice plus call frame per boundary, measured as four allocations for
GetBuffer+Release; reusing Buffer adds no allocations above that boundary cost.
