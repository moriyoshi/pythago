Channel bridge performance, 2026-11-16

Environment and method
Linux arm64, Cortex-X925 fast cores 5-8, GOMAXPROCS=4, Go 1.26.11,
CGO_ENABLED=0, embedded free-threaded CPython 3.14t. The host also has slower
Cortex-A725 cores. The initial unrestricted run had substantial scheduling
variation; pinned measurements are the primary results below.

One operation is one completed channel message, not a request/reply round trip.
Scalar payload: int64(1<<40 + 7), outside Python's small-integer cache.
Interpreter initialization, Python source compilation, channel wrapping, and
loop creation/cleanup are excluded from the timed region. Each bridge test uses
one Python event loop and one native Go producer or consumer. The 32-worker
case uses 32 concurrent Python tasks and reports amortized throughput cost,
not the latency of an individual await. Scalars: five 600 ms samples. Baselines:
three 400 ms samples. Bytes: three 600 ms samples. All values below are medians.
Go allocation metrics exclude the Python heap. No production optimization was
applied as part of this measurement task.

Bottlenecks supported by the profiles
1. Per-message FFI, conversion, and asynchronous scheduling dominate the native
   channel operation. Every await creates a Future, callback, operation state,
   two Go synchronization channels and a worker goroutine, even when the native
   channel is immediately ready. It then returns through the completion queue.
   A success also calls channel_cancel for cleanup. Buffer capacity does not
   bypass this lifecycle, which explains the limited buffering benefit.

   For 100,000 receives, Python profiling counted 100,000 channel_start calls,
   100,000 channel_cancel calls, and 104,717 polls with one task. With 32 tasks,
   polls fell to 3,631: about 27.5 messages per poll. Poll time includes waiting;
   these cProfile totals are not CPU percentages, and profiling adds overhead.

2. Object conversion and wrappers create substantial allocation traffic.
   The scalar Go allocation profile attributed 16.2% of allocated objects to
   py.own, 15.7% to Object.Int64, 11.4% to py.borrow, and 11.1% to py.sequence.
   The isolated Go core is only about 1.1 us; it is not the largest component.
   Go CPU sampling showed substantial callback and scheduler/futex activity.

   Channel dispatch/operations do not use reflection. The shared FFI callback
   trampoline still uses purego.NewCallback -> callbackWrap -> reflect.Value.Call.
   reflect.Value.call accounted for 39.8% inclusive sampled CPU, including all its
   child callbacks; only 1.35% was its own time. Its inclusive allocation total
   likewise includes downstream conversions. Those totals must not be described
   as the cost of reflection alone.

3. Python -> Go byte copying and resulting heap/GC work dominate large-payload
   memory traffic. For 64 KiB messages, Object.Bytes accounted for 96.9% of
   allocated Go bytes. runtime.memmove accounted for 15.35% of sampled CPU, with
   additional GC/scanning activity. Each transfer allocates an independent Go
   byte slice; the Go -> Python direction allocates its byte copy on Python's
   heap, which is absent from Go's B/op column.

4. Locking was secondary in this one-loop workload. The concurrent mutex profile
   attributed about 158 ms of aggregate contended delay to completion posting
   over a 3.7 s run. Handle-registry locking was not prominent. This does not
   establish scaling behavior for multiple concurrent Python event loops.

Recommended optimization order (not implemented or measured here)
- Add typed nonblocking send/receive fast paths. Immediately ready operations
  could return directly without allocating a Future, worker, and completion.
- Remove the successful-operation cancellation round trip; reserve cancellation
  work for actual cancellation. Reduce intermediate Object/tuple construction
  and collapse the recv -> recv_ok -> _channel_wait coroutine layers.
- For large binary transfers, consider an explicit ownership/lifetime-aware
  buffer variant. A plain []byte receiver can retain data after receiving, so a
  safe replacement for the copy needs an ownership contract.
- A typed FFI trampoline could remove purego's remaining reflection, but the
  inclusive callback percentages alone do not predict its possible speedup.

Reproduction (run from repository root with the test image, .work/testimage, generated)
Base environment:
  taskset -c 5-8 env GOMAXPROCS=4 GOTOOLCHAIN=go1.26.11 CGO_ENABLED=0 GOWORK=$PWD/.work/go.work
Append the following Go commands to that environment prefix:
  go test ./aio -run '^$' -bench '^BenchmarkChannelBridge$/(GoToPython|PythonToGo)/Cap(0|64)$/Workers(1|32)$/Int64$' -benchmem -benchtime=600ms -count=5
  go test ./aio -run '^$' -bench '^(BenchmarkChannelCore|BenchmarkNativeChannel|BenchmarkAsyncioQueue|BenchmarkPythonGoCall)$' -benchmem -benchtime=400ms -count=3
  go test ./aio -run '^$' -bench '^BenchmarkChannelBridge$/(GoToPython|PythonToGo)/Cap64$/Workers32$/Bytes(4096|65536)$' -benchmem -benchtime=600ms -count=3
For the unrestricted matrix, omit taskset/GOMAXPROCS and use:
  go test ./aio -run '^$' -bench '^(BenchmarkChannelBridge|BenchmarkChannelCore|BenchmarkNativeChannel|BenchmarkAsyncioQueue)$' -benchmem -benchtime=300ms -count=3
For Python profiles, additionally set:
  PYTHAGO_CHANNEL_PYPROFILE=/tmp/channel.prof
Select a single bridge benchmark and use -benchtime=100000x -count=1.
For Go profiles, select a single bridge benchmark and add:
  -cpuprofile=/tmp/channel.cpu -memprofile=/tmp/channel.mem -o /tmp/aio.test
For contention, separately use:
  -blockprofile=/tmp/channel.block -blockprofilerate=1000000 -mutexprofile=/tmp/channel.mutex -o /tmp/aio.test
Summarize samples:
  python3 bench/channels/summarize.py bench/channels/pinned-scalars.txt bench/channels/pinned-baselines.txt bench/channels/pinned-bytes.txt

Raw data and text profiles are retained in this directory. Native profile files
and their matching binaries are in /tmp/pythago-channel-* and /tmp/pythago-aio*.
The GIL Python variant, other architectures, multi-loop scaling, and per-message
latency distributions were not measured. CPU profiles may not fully resolve
internal Python/native execution, so Python profiles supplement them.
